# 接口模块结构说明（管理端 / 用户端彻底隔离）

> 状态：已上线。用户端 `https://new-api.jdhsf.top`，管理端 `https://new-api-admin.jdhsf.top`。
> 版本：v2.1（2026-09-10），管理端网关 Basic Auth 弹窗已移除（只保留 new-api 管理员登录一道门）；
> 双端 `/api/status` 的 `server_address` 由网关钉为对外域名（CC Switch 等导入入口的官网/端点来源）。
>
> **当前线上拓扑**：两个域名 DNS → Render 云服务（GitHub `wang52001/api-shim` 仓库自动部署，
> 单容器 `edge.py` 按 Host 分流到 user_side/admin_side 两套栈，new-api 在容器内 127.0.0.1:3000）。
> 本机 Mac（launchd 双端口 run.py + Cloudflare Tunnel）为备用/开发环境，代码与仓库保持一致。

---

## 1. 为什么隔离

改造前，`new-api.jdhsf.top` 经 Cloudflare Tunnel → `codex_shim.py:3001` → `new-api:3000` 是**全量透传**：
客户与管理后台共用同一个公网入口，`/console`、`/api/channel`、`/api/option` 等管理接口与
业务接口（`/v1/*`）对外不可区分，管理面暴露在客户可见的同一域名下。

隔离后，两端各自拥有独立的**入口、路由、控制器、服务层、权限校验**，互不可达。

---

## 2. 隔离架构

```
                             Cloudflare Tunnel（同一隧道，两条 hostname 规则）
                                        │
        ┌───────────────────────────────┴───────────────────────────────┐
        │                                                               │
   new-api.jdhsf.top（用户端）                        new-api-admin.jdhsf.top（管理端）
        │ 仅放行：自助 + 业务协议                                   │ 仅放行：控制台 + 管理API
        ▼                                                               ▼
   ┌───────────────────────────┐                          ┌───────────────────────────┐
   │ gateway 用户端 :3001       │                          │ gateway 管理端 :3002       │
   │  user_side 包（独立栈）    │                          │  admin_side 包（独立栈）   │
   │  · LLM 业务（身份伪装转发） │                          │  · Basic Auth 门            │
   │  · 自助 API（白名单）      │                          │  · /v1 /v1beta /pg /mj →404 │
   │  · 管理接口/管理页 → 404   │                          │  · 其余全量转发            │
   └────────────┬──────────────┘                          └────────────┬──────────────┘
                │ 上游 new-api 自身鉴权：                              │ 上游 new-api 自身鉴权：
                │ TokenAuth（sk- 令牌）                                │ 管理员 JWT（role>=10）
                ▼                                                     ▼
   ┌───────────────────────────────────────────────────────────────────────┐
   │                        new-api 本体 :3000（编译二进制）                │
   └───────────────────────────────────────────────────────────────────────┘
```

**关键设计**：
- `new-api` 本体是编译好的二进制，内部路由无法改动；隔离在**自有的网关层**完成，效果等价
  ——两个入口、两套路由表、两套控制器/服务/权限，请求在进入 new-api 之前就被分流或拒绝。
- 两个入口**双层鉴权**：网关层（用户端 TokenAuth 透传 / 管理端 Basic Auth）+ 上游 new-api 层
  （用户端 sk- 令牌 / 管理端管理员 JWT）。任一层不通过即拒绝。

## 3. 模块目录结构

```
new-api/gateway/
├── run.py                      # 总装入口：装配两个独立服务（:3001 用户 / :3002 管理）
├── config.py                   # 纯配置（端口/上游/凭据）——两端唯一共享物，且只共享数据
├── user_side/                  # ══ 用户端（对外售卖）══
│   ├── routes.py               #   用户端路由表（唯一接口面定义处）
│   ├── permissions.py          #   权限校验（LLM前缀 / API白名单 / SPA管理页封禁 / 路径穿越防护）
│   ├── controllers.py          #   控制器（UserSideHandler：分发入口）
│   └── services.py             #   服务层（上游转发 + 三协议身份伪装注入）
├── admin_side/                 # ══ 管理端（内部运营）══
│   ├── routes.py               #   管理端路由表（healthz / 业务前缀封禁 / Basic Auth 门）
│   ├── permissions.py          #   权限校验（Basic Auth + 业务接口封禁）
│   ├── controllers.py          #   控制器（AdminSideHandler：分发入口）
│   └── services.py             #   服务层（上游转发，剥离 Basic 凭据头，无伪装）
├── test_permissions.py         # 权限矩阵单元测试（双端全量断言）
└── gateway_test.sh             # 请求级回归脚本（可指定端口）
```

**隔离纪律（硬约束）**：
- `user_side` 与 `admin_side` **互不 import**，各自持有完整的 routes→permissions→controllers→services 栈。
- 转发实现、日志文件、权限逻辑在两端各自独立（有意少量重复，换取彻底隔离）。
- 唯一交集 `config.py` 只放**配置数据**（端口/上游/凭据），不含任何接口定义。

## 4. 用户端接口面（`new-api.jdhsf.top` → :3001）

### 4.1 请求入口与路由分类

| 类别 | 路径前缀 | 处理 |
|------|----------|------|
| **LLM 业务** | `/v1`、`/v1beta`、`/pg`、`/mj` | 转发到上游并做身份伪装注入（见 4.3） |
| **自助 API** | `/api`（白名单内） | 普通转发，上游按会话/sk 令牌鉴权 |
| **SPA 静态** | 其余（`/`、`/console/token`、`/assets`…） | 普通转发 |
| **管理接口/管理页** | `/api`（白名单外）、`/console/channel`、`/console/user`… | **404**（接口"不存在"） |

### 4.2 自助 API 白名单（方法敏感）

放行（示例，完整清单见 `user_side/routes.py`）：
- **公开**：`/api/status`、`/api/pricing`、`/api/notice`、`/api/setup`(GET)、`/api/models`(精确 GET)、`/api/user-agreement`、`/api/privacy-policy`、`/api/about`、`/api/home_page_content`、`/api/rankings`、`/api/ratio_config`、`/api/uptime/status`…
- **登录/注册**：`/api/user/login`(POST)、`/api/user/register`、`/api/user/reset`、`/api/oauth/*`、`/api/verify*`…
- **自助账号**：`/api/user/self`、`/api/user/models`、`/api/user/token`、`/api/user/sessions*`、`/api/user/passkey*`、`/api/user/2fa*`、`/api/user/checkin`、`/api/user/aff*`、`/api/user/topup`(**POST=兑换码兑换**)、`/api/user/setting`…
- **自助数据**：`/api/token/*`、`/api/log/self*`、`/api/log/token`、`/api/audit/self`、`/api/data/self`、`/api/data/flow/self`、`/api/mj/self`、`/api/task/self`、`/api/task/*/artifacts`、`/api/usage/token`。

封禁（返回 404，方法敏感）：
- `/api/channel/*`、`/api/option/*`、`/api/redemption/*`、`/api/models/*`(子路径)、`/api/group/*`、`/api/prefill_group/*`、`/api/vendors/*`、`/api/deployments/*`、`/api/performance/*`、`/api/ratio_sync/*`、`/api/plugin/task*`、`/api/task_plugin_options`、`/api/authz/*`、`/api/system-task/*`、`/api/system-info/*`、`/api/subscription/*`、`/api/audit`(精确)、`/api/status/test`、`/api/setup`(POST)、支付回调 `stripe/creem/waffo webhook`、`/api/custom-oauth-provider/*`…
- `/api/user/` 下非自助动作：`GET /api/user/`、`POST/PUT /api/user/`、`/api/user/:id`、`/api/user/search`、`/api/user/manage`、**`GET /api/user/topup`**（管理员查所有充值，与 POST 自助兑换同路径不同方法）、`/api/user/2fa/stats`…

### 4.3 LLM 业务身份伪装

对以下三类协议改写请求体（与上一版 shim 逐行等价，已全量实测）：
- OpenAI Responses（`/v1/responses`）：修正 input item id 前缀 + 往 instructions 注入身份
- Anthropic Messages（`/v1/messages`）：往 system 顶部注入身份
- Gemini（`/v1beta/*`）：往 systemInstruction 顶部注入身份

注入内容：「当前会话使用的模型名称是「X」。被问时直接回答：我是 X……」。

### 4.4 视觉回落（图片感知路由，2026-09-10 新增）

33 个假名映射的真实模型全是纯文本模型。网关在转发前检测请求体中的图片内容
（`image_url` / `input_image` / `image` / `inline_data`），若模型是假名则临时改写为视觉模型：
- 旗舰假名 → `qwen-vl-max`；flash/mini/nano/lite/haiku 档 → `qwen-vl-plus`（按 `-` 分段匹配）。
- 纯文本流量仍走原映射不变。覆盖 `/v1/responses`、`/v1/messages`、`/v1beta`、`/v1/chat/completions`。
- **兜底**：上游拒绝回落调用时（无渠道 / 令牌 model_limits 不含视觉模型 / 配额等 4xx），
  自动用原始请求重试一次，退化为未回落的原生行为（glm 系静默忽略图片 / qwen 系报模态错误），不回归。
- 回落真正生效需要：对应分组有 qwen-vl-* 渠道能力（abilities）且令牌 model_limits 放行该模型。
  本机已配：default 组 abilities += qwen-vl-max/plus、wjw 账号分组 → vip。

### 4.5 响应 model 字段恢复（2026-09-10 新增）

new-api 经 model_mapping 改写后会把真实模型名透传在响应 `model` 字段里（既有泄漏，
如客户收到 `glm-5.2`）。网关统一把 LLM 响应的 model 恢复为客户请求的模型名
（非流式改 JSON，SSE 按行替换 `"model":"..."`；字符串值内转义序列不会误匹配）。

> ⚠️ 已知边界（沿用旧版行为）：`/v1/chat/completions`（OpenAI Chat 协议）**未做**身份注入
>（该协议无 system 字段，注入会被上游拒绝；视觉回落与模型名恢复对其生效）。

### 4.6 权限校验逻辑（用户端）

1. 路径穿越/编码绕过防护：含 `..`、`//`、`%2e`、`%2f`、`%5c` 的路径一律 404。
2. `/v1 /v1beta /pg /mj` → 直接透传，**鉴权交给上游 new-api 的 TokenAuth（sk- 令牌）**。
3. `/api/*` → 命中白名单则透传（鉴权交给上游会话 Cookie / 令牌）；否则 404。
4. 其余（SPA）→ 管理页前缀 404，其余透传。

## 5. 管理端接口面（`new-api-admin.jdhsf.top` → :3002）

### 5.1 请求入口与路由分类

| 类别 | 路径 | 处理 |
|------|------|------|
| **存活探针** | `GET /healthz` | 200，免鉴权 |
| **业务接口** | `/v1`、`/v1beta`、`/pg`、`/mj` | **404**（业务只属于用户端） |
| **其余一切** | `/`、`/console/*`、`/api/*`… | Basic Auth 通过后全量转发 |

### 5.2 权限校验逻辑（管理端）

1. **业务封禁（网关层）**：`/v1 /v1beta /pg /mj` 前缀一律 404，业务接口在管理端"不存在"。
2. **鉴权（上游一道门）**：其余请求全部普通转发，由上游 new-api 自身的管理员登录
   （JWT role>=10）把关——未登录访问 `/api/channel/` 等管理接口返回 401。
   （2026-09-10 起移除网关 Basic Auth 弹窗：两层弹窗体验差，且 Basic 凭据固定、
   防护价值有限；管理面真正的防线是 new-api 的管理员账号。）

### 5.3 凭据头剥离

网关在转发前剥离自身的 `Authorization: Basic ...`，避免 new-api 误读为 API 令牌；
new-api 真正的会话凭据（Cookie / `New-Api-User` / Bearer 令牌）原样透传。

## 6. 隔离保证与验证

| 保证项 | 实现 | 验证结果 |
|--------|------|----------|
| 用户端无法触达管理接口 | `/api` 白名单 + 管理页 404 | 公网 `/api/channel/`、`/api/option/`、`/api/user/` 均 404 |
| 管理端无法触达业务接口 | `/v1 /v1beta /pg /mj` 前缀 404 | 公网管理域 `/v1/models` 404 |
| 两端不共享接口定义 | 各自独立 routes/permissions/controllers/services，互不 import | 代码审查 + 权限矩阵单测 |
| 管理端鉴权 | 上游 new-api 管理员 JWT（网关 Basic Auth 已于 2026-09-10 移除） | 未登录访问管理 API 401 |
| 官网/端点不错配 | 双端 `/api/status` 的 `server_address` 网关钉为 `https://new-api.jdhsf.top` | CC Switch 导入显示正确域名 |
| 身份伪装不回归 | 三协议注入逻辑逐行迁移 | 实测 `/v1/messages` 回答「我是 Claude Sonnet 4.6」 |
| 客户模型列表不泄露 | 白名单透传 | cc-claude `/v1/models` 返回 11 假名、无真实名 |
| 路径穿越 | 非法路径段 404 | `test_permissions.py` 全绿 |
